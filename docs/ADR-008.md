# ADR 008: Secure Server-Sent Events (SSE)

## Context
Providing real-time progress updates for background jobs requires a persistent connection. WebSockets add significant overhead and require custom load-balancing logic. SSE is simpler but vulnerable to connection drops via proxy timeouts and unauthorized access.

## Decision
We use native HTTP Server-Sent Events backed by Redis Pub/Sub, hardened with:
1. Strict database queries verifying the requested Job ID belongs to the authenticated user's workspace before initiating the stream.
2. A 15-second heartbeat interval emitting empty packets (`: heartbeat`) to prevent Nginx/AWS load balancers from dropping idle connections.
3. Explicit cleanup on client `abort` or terminal job states.

## Consequences
- **Positive:** Secure, highly scalable, real-time UX without the infrastructure complexity of WebSockets.
- **Negative:** Requires a dedicated Redis connection per subscriber, which may require pooling or horizontal scaling under extreme load.
